# "m" 菜单脚本文件 — 已证实事实与未解问题 (JD+11 修订)

## 已证实 (字节码证据)

- 头 2 字节 `19 00`: j.ctor 读 `n2 = d(2)` (u8) = 25; `f.b = new int[25]` — **25 个屏幕/节点**。
- 头表: 9×int32 (b[9], ctor :66-68 读), j.a() 原样转交渲染器 i.a(int[])。
  字节观察 [1..36] 为 u16 对形态 (86,89,87,85,236,256,258,260,262,282,280,300,360,362,417,…),
  数值域与语言包序号/屏 id 相符, 但**读法存疑** (见下)。
- b(int): 每次新建流, 定位序列为 `skipBytes(-(2n-1)) → readShort → skipBytes(-L) → readU8(屏型) → …`;
  屏型 i ∈ 0-7 的分派在源码 switch (型 0 菜单/1 图文/2 消息/3 录入/5/6 设置/7 条件跳转)。
- 屏型 → screenMode: 4→1, 5→2, 6→3, 其余→0 (:146-163)。
- FIRE/BACK 动作位、历史栈 f.b、设置对写入均见 j_clean。

## 未解 (反编译源不足以定标)

- `skipBytes(负数)` 在 MIDP 标准语义下返回 0 不回退 — 按字面模拟, 所有屏都从字节 0 读,
  25 屏退化为同一内容, 与"25 屏树"矛盾。可能解释:
  1. 诺基亚专有 DataInputStream 行为 (负 skip = 绝对定位或循环回绕) — 需真机/模拟器验证;
  2. CFR 对该段反编译失真 (offset 计算被内联改写) — 需对照字节码 (javap -c)。
- 在上述两点解决前, **逐屏数据解析无法定案**。j 的解释逻辑 (代码侧) 已完整, 缺的只是
  "m" 的可靠游标语义。
